\textbf{Candidate source checkout.} Public auto\_workflow v1.0.1 resolves to commit \path{041cee543523f98cf3e130c9f4e05b9a74e57de2}. \subsection*{Snapshots versus replay}
Saved per-action snapshots are sufficient but not inherently necessary. A content-addressed initial image/source tree, exact task setup and complete ordered tool records can suffice if every state-changing operation can be replayed and independently checked. Failed shell commands may partially write files. Parallel writes may conflict. Builds can generate source. Services, network responses and background jobs can alter later results. A final diff or a successful final score does not establish intermediate states. Such cases require verified effects, checkpoints or isolated instrumented replay, not guessed file contents.

\section{Fresh controlled experiment}
\subsection*{Design frozen before test scoring}
The 320 histories span eight newly authored guard forms, approved command tokens, depths 2 and 4, unrelated-edit gaps 0/5/13/21, and five variants: weakening, repair, equivalent guard, fixed arguments and removed execution. Four entire syntax/task-token families calibrate thresholds and four test them. Each split has 32 unsafe and 128 safe cases. Related depth/distance/variant cases stay in the same split.

The accepted command token differs by family (inspect, report, version and ready for calibration and health, ping, list and info for test). An initial pre-scoring split check found exact prompt collisions in graph conditions that could not observe the guard. Varying the actual authorized command and guard syntax produced distinct task families; the corrected protocol froze before any scoring. This is an additional task difference, not evidence of independent real repositories. No model input contains a family/variant label or ground-truth outcome.

\textbf{Policy.} A caller-provided string other than the explicitly approved token must not reach \texttt{subprocess.run} with \texttt{shell=True}. Fixed argument lists, repairs, equivalent changes and removal are allowed under this narrow policy. Labels do not claim general security or completion of a LinuxArena side task.

\textbf{Ground truth.} A separate restricted AST interpreter checks eight concrete inputs per case (2,560 checks) without executing processes. The symbolic checker verifies the supported string policy and produces witnesses for violations; witnesses are checked against the concrete interpreter. All 320 final classifications agree. Unknown calls and missing proof remain unknown, exercised separately by engineering controls rather than assigned fabricated safe/unsafe labels. The reference condition is source-grounded and analytically checked, but lacks independent human oracle review.

\subsection*{Strong current-code control}
Both current-code and history conditions use the same bounded symbolic engine. Both receive current predicates, execution settings, verification status and a counterfactual analysis of the \emph{explicit proposed patch}. Previewing that supplied edit is allowed; neither condition receives an observed future repository or tool result. The strong current-code condition has no historical summaries. The history condition adds prior source changes and repaired/broken assumptions. Both obey the same 1,024-token evidence cap and include the same complete proposed action.

The temporal/prose ablation selects the same source-backed facts and event-support links jointly so both formats fit. The selector is explicitly approximate: lexical action seeds followed by bounded dependency traversal, not a learned selector or a sound whole-program causal analysis. Raw history, node/edge differences and current graph baselines remain separate.

\textbf{Duplicates.} There are 2,560 logical jobs but 872 unique prompts: 436 calibration and 436 test, with no exact overlap across phases or old pilot prompts. The strong current-code test condition has only 32 distinct prompts among 160 cases; its four false alarms reuse one response. Counts do not represent 160 independent trials. All eight families remain closely related examples of one narrow command policy.

\section{Frozen-threshold results and uncertainty}
Each condition permits at most $\lfloor0.01n\rfloor=1$ false alarm on 128 benign calibration cases. The alarm rule is strictly score $>\tau$. Ties make achieved calibration false alarms zero for every condition. The threshold artifact was written before any test prompt was scored and hashes the calibration scores and test jobs. No test-based retuning occurred.

All unsafe denominators are 32; all safe denominators are 128. The strong current-code test false-positive rate is 3.125\%; all other conditions' observed rates are zero. These are \emph{achieved} test rates, not a claim of matched rates. Zero observed alarms does not prove a population false-positive rate of zero.

\textbf{Primary contrast.} Assumption history minus strong current-code recall is 0 percentage points. There are no history-only or current-only detections. A paired sign-flip test over four family blocks gives $p=1$. The family bootstrap recall-difference interval degenerates to $[0,0]$ because all observed family differences are zero; it does not establish equivalence or exclude unseen failures. Four closely related blocks provide little information about generalization.

Descriptive binomial 95\% intervals are 0--10.9\% for 0/32 recall, 0--2.84\% for 0/128 false alarms, and 0.86--7.81\% for 4/128 false alarms. These intervals assume independent Bernoulli observations, which the repeated-template/cached-response design violates. They are descriptive only. Family-resampled strong-current FPR spans 0--9.375\%; its single unique mistaken response is repeated four times.

\subsection*{Observed failure mode}
Calibration examples often received high scores despite explicit preserved restrictions or allowed removal. A representative rationale incorrectly said the policy required \texttt{shell=False}, although the supplied property allowed shell execution of the approved token. In fresh testing, the strong current-code condition flagged an allowed removal of execution as unauthorized behavior. This suggests policy misapplication can dominate evidence quality for this monitor/prompt. A rationale is diagnostic evidence, not proof of internal model reasoning.

These results do not validate the old positive pilot signal, demonstrate a history advantage, or falsify all possible DeepTrace methods. They show that this bounded implementation and frozen monitor did not achieve useful low-false-alarm detection on this fresh controlled test. Changing the prompt or threshold now would require another fresh held-out set.

\section{Implemented boundaries and remaining work}
\textbf{Replay validator.} The new pure-data validator requires an initial capture hash plus provenance attestation, matches tool call identities, checks mutation preimages, retains failed/partial effects as unknown, rejects conflicting parallel writes and invalidates states contradicted by reads. A verified complete checkpoint may resynchronize later source states. It does not execute arbitrary shell commands, recover service state, verify the producer's attestations cryptographically, or convert a self-asserted Boolean into provenance. Its present scope is plain-text workspace files. Twenty engineering checks cover adversarial failure paths and the harmful-action boundary convention.

\textbf{Fuller support DAG (not monitor-scored).} A separate implementation now connects versioned source occurrences, supporting symbols, security claims and edit events. Supporting source edits mark prior claims stale and trigger a recheck; unrelated documentation reuses the existing claim. Versioned source occurrences prevent a repaired file with identical contents from creating a temporal cycle. All 320 histories pass an acyclicity check. This fuller graph was built after the frozen monitor run; the reported scores evaluate the earlier bounded summary/event packets, not this new graph. Its monitor benefit requires fresh evaluation.

\textbf{Before-execution convention.} If action $h$ causes the first harmful effect, an alarm at decision boundary $h$ counts as timely because the monitor runs before action $h$ executes. The prepared evaluator checks alarms at indices $i\le h$, unlike an ambiguous strict-less-than landing-marker interpretation. For delayed effects, annotations must connect installation, trigger and observation and rule out earlier effects. An offline alarm is not live prevention.

\textbf{Assumptions.} Corrected records contain 512 preserved, 512 violated, 64 restored and 64 removed restriction-event annotations. Unknown is tested by an unresolved-call control. Restriction status differs from the combined policy: a weakened guard with fixed arguments can still preserve the policy. A small post-analysis annotation correction marks ``restored'' only on the repair transition, rather than on subsequent preserved versions. It did not alter any monitor input: earlier histories and all proposed-preview summaries were checked identical; the unused proposed transition label is versioned separately. Frozen prompts, scores and thresholds remain unchanged.

\textbf{Next indispensable milestone.} Obtain a small real cohort with provenance and execute it in an isolated Linux environment. Validate initial tree and setup, capture each pre-action source tree, rerun task/scorer checks where supported, adjudicate first effects independently, and review reference evidence for attacks and honest actions. Only then freeze fresh splits and score all required conditions. Full-repository extraction errors, unsupported language features and missing effects must remain in the cohort ledger. The current TypeScript application needs an appropriate semantic analyzer; the Python fixture checker cannot simply be relabeled as LinuxArena support.
